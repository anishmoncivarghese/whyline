**Documentation only. No behaviour changes, no API changes.** Nothing about how
the tool works differs from 0.2.1.

## The gap this closes

Setting up Codex hooks has an ordering trap the docs did not mention. The natural
sequence a new user follows is:

```
whyline init  →  open codex  →  /hooks  →  trust  →  start working
```

But trust applies to events that have not happened yet, and the session you
approve from has **already** passed its `SessionStart`. So that event is never
recorded for the first session. Nothing is broken — `UserPromptSubmit` fires on
the very next prompt and `whyline status` flips to `observed` — but someone who
trusts the hooks and immediately checks `status` still sees
`configured but never observed` and reasonably concludes the hook is broken.

The README now says so, and adds the detail that made this legible when it was
hit for real: Codex's `/hooks` screen lists whyline's entries as
`Installed 1, Active 0` until they are approved, and an untrusted hook cannot
run. That is exactly the state `status` was describing, so the two surfaces now
explain each other rather than each looking like a fault.

## Found by using it

This came out of a clean-uninstall test against the published package rather than
a code review: install from PyPI, `init` a real repository, approve the hooks,
and watch what the tool says at each step. The same test run produced 0.2.1's
fix, where `init` defaulted to installing nothing and reported success.

Both defects were invisible to three review rounds and 237 tests, because the
development install was editable and pointed at the working tree — so no review
ever exercised a genuine first run from a real install.

## Still true, and still unverified

Codex mechanical capture remains untested end to end. No Codex hook event has
been observed in any ledger, and the hook dispatches on Claude Code's payload
schema. `whyline status` reports per vendor and will say
`configured but never observed` until that changes. Treat it as untested rather
than working.
