A `note` that failed halfway could leave the two stores disagreeing, with the
committed one — the only one a clone sees — missing the decision.

## `note` could silently diverge its two stores

whyline keeps two: `.whyline/decisions.md`, which is committed and is therefore
all a fresh clone has, and `.whyline/ledger.jsonl`, which is gitignored because it
holds raw prompt text.

0.1.1 wrote the ledger **first**. If the second write then failed, the note lived
in the local ledger only: `brief` and `status` both reported it while
`decisions.md` did not have it. Two stores disagreeing, with no error — and the
surviving copy was the one that does not travel.

`decisions.md` is now written first, so the one remaining failure direction is the
safe one: if only the local ledger fails, the note is still durably recorded where
a clone will find it, and `brief` recovers it by parsing the Markdown.

`note` also raised a raw traceback instead of a clean message, unlike every other
command, and a partial write said nothing about what had and had not been stored.
Both fixed; a partial write now names exactly which store holds the note.

This is not a hypothetical. It was found by probing what happens when storage is
unwritable — a case a sandboxed agent genuinely hits, since Codex's
workspace-write sandbox had already blocked `.git` during a real delegated task.

## A performance test that failed for the wrong reasons

The import-cost test had been rewritten twice and was still measuring the wrong
thing. An absolute 200 ms budget failed CI, where one macOS runner spent 215 ms on
interpreter startup alone. A ratio against that baseline was meant to be machine
independent and is the opposite: a *faster* machine has a smaller baseline, so
identical import cost yields a *larger* ratio — 0.45 locally, 1.01 on CI, failing
a limit of 1.0 while nothing was wrong.

It now counts modules, which is exact, identical on every machine and every run,
and has a large signal: `whyline.cli` pulls in 36 modules where a single
`import asyncio` pulls in 102. A loose absolute timing cap remains as a backstop,
since a module doing heavy work at import time would import few modules and slip
past a count check.

## A limit on the headline result, recorded

M0 measured agents recording decisions at 150% and 130% of their non-trivial
changes. This release records where that does *not* hold: a full orchestrated
cross-vendor task — one agent planning, another implementing, a reviewer finding a
real bug in the plan's own algorithm — produced three commits and **zero** whyline
decisions, because the reasoning went into a gitignored tracker instead.

The rate is a property of an agent working directly, not a general one. Stated in
the README rather than left to be discovered.

*These notes were written retroactively, in 0.1.3, from the commit history and
the project's own decision record. This release shipped without them.*
